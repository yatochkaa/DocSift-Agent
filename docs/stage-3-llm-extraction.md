# Этап 3. Извлечение через LLM

## Провайдеры

`LLMProviderProtocol` задаёт единый async-интерфейс. Реализованы:

- `OllamaProvider` — локальный `/api/chat`;
- `OpenAICompatibleProvider` — `/chat/completions` любого совместимого API.

Провайдер, URL, модель, таймаут и поддержка нативной схемы меняются настройками
`DOCSIFT_LLM_*`. Секрет API читается как `SecretStr` и никогда не сохраняется в
`provider_settings`.

## Structured output

Для Ollama JSON Schema передаётся в `format`. Для OpenAI-совместимого API используется
`response_format.type=json_schema` со строгой схемой. Если выбранная модель или сервер не
поддерживает этот режим, `DOCSIFT_LLM_NATIVE_STRUCTURED_OUTPUT=false`: полная JSON Schema
добавляется в system prompt, затем ответ всё равно обязательно проверяется Pydantic.

Нативная схема снижает число синтаксических ошибок, но не заменяет серверную валидацию:
контрольная сумма ИНН, даты и суммы проверяются только после ответа.

## Ретрай и защита от выдумок

Всего выполняются максимум две попытки. После битого JSON или ошибки схемы второй запрос
получает сырой ответ и точный текст `ValidationError`. Версионируемый prompt `v1.md` требует
для отсутствующих данных `value=null`, `confidence=0`, `sources=[]` и запрещает угадывать
значения.

## Аудит

Одна строка `extractions` хранит версию и полный фактический prompt, модель, провайдера,
последний сырой ответ, журнал обеих попыток, input/output tokens, суммарное время ответа,
валидированный JSON и ошибку. Это позволяет этапу evals воспроизводить и сравнивать прогоны.

В журнал и БД попадает содержимое коммерческих документов. В production нужны шифрование
дисков и резервных копий, ограничение tenant-доступа и политика удаления данных.
